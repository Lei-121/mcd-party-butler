# 麦当劳派对管家

**mcd-birthday-party-butler** · 一个基于麦当劳 MCP 的 WorkBuddy Skill

> 把「在麦当劳给孩子办一场生日派对」这件事，从翻 50 多家门店、猜哪天能约、读懂几千字须知，压缩成一次对话。

---

## 一、项目介绍

### 要解决的问题

麦当劳的派对预约（生日派对 / 主题派对 / 麦麦体验营 / 品鉴会 / 读书会）是一项客单价 275–660 元、但决策链路极长的服务。用户在官方渠道完成一次预约，需要依次做出 6 个选择：

**派对商品 → 城市 → 门店 → 日期 → 场次 → 下单**

我们在真实环境实测后，发现了 4 个让用户大量流失的摩擦点：

| 摩擦点 | 实测数据 |
|---|---|
| 商品过多 | 派对类商品一次性返回 **26 个**，价格从 25.9 元到 198 元不等 |
| 筛选信息不全 | 列表接口**不返回适龄、人数、成团方式等属性**，判断"这个派对适不适合"必须逐个查详情 |
| 门店过多 | 仅深圳、单款派对商品就返回 **54 家**可办门店 |
| 日期不确定 | 实测当天为 10-10，某门店最早可约已是 **10-17**、全天仅 **3 天**可选 |
| 规则不透明 | 决定成败的规则（成团人数、提前预订天数、加价规则、退订政策）全部藏在几千字的购买须知长文中 |
| 结果不可复用 | 门店集合与可约日期随商品变化——换一款派对商品，门店从 **54 家**变成 **32 家**，同一门店的可约日期从 **3 天**变成 **0 天** |

前三条让用户"翻到累"，第四条让用户"看懂之前就可能选错"，第五条连官方 APP 都容易让人卡住。而生日派对是一场**不容失败**的活动——选错了没有补救机会。

### 这个 Skill 做了什么

它替用户跑完 6 级下钻，只输出 2–3 个可直接执行的方案，并把风险用几句人话讲清楚。

### 核心设计：五条规则

1. **先查后问。** 可约日期必须先从接口取到真实数据，再让用户在真实存在的选项里挑。禁止先问"你想哪天"再验证——用户想要的日子很可能根本不可约。
2. **门店收敛。** 一次返回 54 家门店时，按距离排序只展示 3–5 家，并交代总数。用户会在长名单里迷路，而这正是流失发生的地方。
3. **须知翻译。** 把几千字的购买须知提炼成四句人话：提前几天预订、人数上下限、每加一位加多少钱、退订和缺席政策。
4. **模式决策辅助。** 只有当商品允许两种模式时才询问用户；对"生日不能失败"的场合，主动提示拼团不成团退款的风险。
5. **结果不复用。** 门店、日期、场次都是「商品 × 城市/门店」维度的结果。换商品必须重新下钻，禁止沿用上一次的门店编码。
6. **两段式筛选。** 列表接口没有年龄，也没有任何派对属性，所以筛选必须分两层：列表层用类目、名称、价格粗筛，详情层再用适龄、人数精筛。绝不假装能在列表阶段按年龄过滤。

## 二、目标用户

**主要用户：为孩子筹办生日的家长。**

他们在意的是"这场活动能不能顺利办成"，而不是"菜单上有什么"。典型的使用时刻是：孩子下个月生日，家长打开手机想订个地方，然后被几十家门店和一堆日期选项劝退。

**次要用户：代为策划的人**（亲友、公司行政、亲子社群组织者）。他们的场景与家长高度重合，只是需要把方案转达给决策者，因此本 Skill 的输出格式被设计成**可以直接转发**的结构化方案。

**不适用场景**：单人用餐、普通点餐、外卖下单——这些不在本 Skill 的职责范围内。

## 三、安装方法

本仓库的**根目录即技能目录**，安装只需把整个文件夹复制到技能目录下。

### 方式一：安装为用户级技能（推荐，所有项目可用）

```bash
cp -r mcd-birthday-party-butler ~/.workbuddy/skills/
```

### 方式二：安装为项目级技能（团队协作时使用）

```bash
mkdir -p .workbuddy/skills
cp -r mcd-birthday-party-butler .workbuddy/skills/
```

### 验证安装

安装后目录结构应为：

```
~/.workbuddy/skills/mcd-birthday-party-butler/
├── SKILL.md
└── references/
    └── mcp-chain.md
```

### 前置条件

- 已连接**麦当劳 MCP Server**（提供 `mcp__mcd-mcp__*` 系列工具）
- 已登录麦当劳会员账号（查询门店、场次与下单都需要身份）
- 仅适用于**中国内地**门店，不含港澳台地区

## 四、使用示例

### 示例一：完整的方案推荐

**用户：**

> 孩子 8 岁生日，想在深圳南山办，大概 6 个小朋友，下周末

**Skill 的行为：**

1. 先拉全部派对商品（26 个），在列表层按类目与价格粗筛；再对候选逐个查详情，用适龄范围精筛出 2–4 个
2. 定位深圳，查出 **54 家**可办门店，只展示最近的 5 家
3. **先查日期再问用户**——实测该门店只可约 10-17 / 10-18 / 10-19
4. 查出场次与余位
5. 输出可直接执行的方案：

```
【方案一】四小福永远好朋友派对常规版
门店：麦当劳深圳皇岗村餐厅（2.1km）
日期：2026-10-17（周六）
场次：15:30–17:00（余位 12）
模式：包场 · 6 位小朋友
总价：约 348 元（58 元 × 6）
提醒：需提前 3 天预订，退订同样需提前 3 天，当天缺席不退
```

6. 等用户确认后才会真正下单

### 示例二：解释"包场"和"拼团"

**用户：**

> 包场和拼团有什么区别？我该选哪个？

**Skill 的行为：** 读取**当前商品**的购买须知原文，转述为：

- **包场**：独占一个场次，需满足最低人数要求
- **拼团**：与其他家庭拼一场，**如果没达到成团人数，预约会自动取消并退款**——存在"白等一场"的风险

并针对"孩子生日不能失败"这一点，给出倾向性建议。

### 示例三：用户的期望日期不可约

**用户：**

> 我想订 10 月 12 号

**Skill 的行为：** 明确告知该日期不在可约范围内，并给出实际可约的日期选项——而不是等用户填完全部信息后才发现订不了。

## 六、使用的麦当劳 MCP 能力

本 Skill 调用了麦当劳 MCP Server 的 **7 个 Tool**，构成一条完整的六级下钻链路：

| 环节 | Tool | 作用 |
|---|---|---|
| ① 选商品 | `mall-points-products` | 拉取五类派对商品 |
| ① 选商品 | `mall-product-detail` | 获取 SKU、适龄、人数、须知原文 |
| ② 选城市 | `query-party-city` | 查询可办城市 |
| ③ 选门店 | `query-party-store` | 查询城市下可办门店 |
| ④ 选日期 | `query-party-store-date` | 查询门店可约日期 |
| ⑤ 选场次 | `query-party-store-session` | 查询场次、余位、成团人数 |
| ⑥ 下单 | `party-order-create` | 创建派对订单 |

完整的入参、返回字段与实测样本见 `references/mcp-chain.md`；业务价值分析见 `MCP_INTEGRATION.md`。

## 七、边界与合规

- 本 Skill 不存储任何用户数据，不进行任何外部网络请求，仅通过麦当劳官方 MCP 完成查询与下单。
- 涉及真实支付的下单操作，**必须经用户二次确认后**才会执行。
- 所有价格、场次、余位均以接口实时返回为准；文档中的实测数据仅用于说明结构与单位，不作为承诺。
- 本 Skill 仅适用于中国内地麦当劳门店。
